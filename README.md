# Screener_backend

## Требования

- Docker с поддержкой Linux-контейнеров
- Docker Compose v2
- Make

Go для запуска через Docker устанавливать не требуется.

## Запуск

Скопируйте пример настроек:

```bash
cp .env.example .env
```

Запустите окружение:

```bash
make up
```

Команда соберёт образ приложения, запустит PostgreSQL и приложение.
Приложение запускается после успешной проверки готовности PostgreSQL.

Проверить состояние контейнеров:

```bash
docker compose ps
```

Приложение доступно по адресу [http://localhost:8080/api/v1/](http://localhost:8080/api/v1/).
Ожидаемый ответ:

```json
{"status":"ok"}
```

## Настройки

Настройки задаются в `.env`. Пример находится в `.env.example`.
Файл `.env` не добавляется в Git.

`DATABASE_URL` формируется Docker Compose из настроек `POSTGRES_USER`,
`POSTGRES_PASSWORD` и `POSTGRES_DB`. Они определены выше строки подключения
в файле настроек. Для значений со специальными символами URL может потребоваться
URL-кодирование при составлении строки подключения.

PostgreSQL доступен приложению по адресу `postgres:5432`, а с компьютера —
по адресу `localhost:${POSTGRES_PORT}`. `POSTGRES_PORT` задаёт порт компьютера;
порт PostgreSQL внутри контейнера остаётся `5432`.

## Остановка

```bash
make down
```

Данные PostgreSQL сохраняются в named volume и доступны после повторного `make up`.

## Просмотр логов

```bash
docker compose logs -f app
docker compose logs -f postgres
```

Для выхода из просмотра логов нажмите Ctrl+C.

## Логирование

Сервис пишет логи в stdout через `log/slog`.

| Переменная | Значения | По умолчанию |
|---|---|---|
| `LOG_LEVEL` | `debug`, `info`, `warn`, `error` | `info` |
| `LOG_FORMAT` | `text`, `json` | `text` |

На каждый HTTP-запрос пишется одна запись access-лога с уровнем `info`. Исключение:
запросы к `/healthz` и `/readyz` (точное совпадение пути) не пишутся, потому что
проверки состояния идут каждые несколько секунд и создают шум.

Пример записи:

```json
{"time":"...","level":"INFO","msg":"http request","method":"GET","route":"/api/v1","status":200,"duration_ms":0.5,"request_id":"test-123"}
```

`route` содержит шаблон маршрута, а не фактический путь. Для неизвестных путей
пишется `unmatched`.

Идентификатор запроса берётся из заголовка `X-Request-ID`, если в нём от 1 до 64
символов `a-z`, `A-Z`, `0-9`, `-`, `_`. Иначе сервис создаёт новый. Идентификатор
возвращается в заголовке ответа и доступен в коде через
`httpmw.RequestIDFromContext(ctx)`.

Паника в обработчике записывается с уровнем `error` вместе со stack trace, клиент
получает `500` и `{"error":"internal server error"}`.

Access-лог не содержит заголовков, тел запросов и query-параметров: в них бывают токены и пароли, а логи доступны более широкому кругу людей и долго хранятся.

Логгер ничего не маскирует автоматически. В своих записях и текстах `panic` не передавайте токены, пароли, заголовок `Authorization` и тела запросов.
